# 0002. 市場資料擷取與圖表技術選型

* 狀態：accepted
* 日期：2026-08-18

## 背景與問題陳述

Happy_Trade 的第一版儀表板需要 BTC/USDT 的價格資料，同時也要當作後續 AI 訊號與模擬交易估值的輸入。系統必須畫出 K 線與技術指標，但不能把行情供應商直接暴露給瀏覽器，也不能因此引入任何真實下單能力。

## 決策考量因素

* 第一版要小、要看得懂、要好驗證。
* 供應商專屬的回應格式不可以外洩到 React 端。
* 不使用交易所金鑰，不具備任何下單能力。
* 之後要能升級成串流資料，且不必更動前端的 API 契約。
* 圖表函式庫要輕量、開源，且支援 K 線與指標疊圖。

## 評估過的方案

1. React 直接呼叫行情供應商，並嵌入供應商託管的圖表 widget。
2. Spring Boot 取用 Binance Spot 公開 REST 行情、正規化後對外提供自有 REST 端點，React 端以 Lightweight Charts 繪製。
3. Spring Boot 從第一版就維持與行情供應商的 WebSocket 連線，主動推播給 React。

## 決策結果

選定方案：**方案 2**。後端以 Binance Spot 的公開 REST 端點（`/api/v3/klines`、`/api/v3/ticker/24hr`）作為 BTC/USDT 行情轉接層，正規化並快取後，對外提供應用自有的唯讀端點 `GET /api/market/ticker` 與 `GET /api/market/chart`；前端以 Lightweight Charts v5 的 Panes API 繪製 K 線、成交量、EMA／SMA、RSI 與 MACD。

資料更新採**前端輪詢驅動的 pull-through 快取**，後端沒有排程任務（沒有任何 `@Scheduled`）：

* 前端依內容調整輪詢節奏——ticker 固定 5 秒；chart 依 K 棒週期從 1m 的 20 秒到 1d 的 300 秒（`CHART_POLL_MS`）。
* 請求進到後端後先查 Caffeine 快取（`marketChart` TTL 15 秒、`marketTicker` TTL 3 秒）；命中就直接回，未命中才即時呼叫 Binance。因此對上游的請求頻率由快取 TTL 決定，不會隨著開幾個分頁等比放大。
* 指標一律在後端算完再回傳（SMA200／EMA15-30-45-60／RSI14／MACD 12-26-9），並多抓 200 根暖機 K 棒後裁掉，讓每條指標序列與回傳的 K 棒索引對齊。

WebSocket 串流明確延後。前端不得直接呼叫 Binance。行情轉接層只能使用公開、唯讀的端點；交易所金鑰、簽章請求、帳戶端點與下單端點一律禁止。

### 正面影響

* 前端的 API 契約與行情供應商解耦，換供應商不影響前端。
* 上游失敗、限流與格式正規化集中在後端一處處理（429/418 對應 503 並讀取 `Retry-After`、451 地區封鎖對應 503、逾時對應 504）。
* 指標計算在後端，前端不必重算，也讓之後的 AI 訊號可以共用同一份計算邏輯。
* 完全符合本專案「不可直接自動下單」的安全紅線。
* 圖表層輕量且完全在應用掌控之內。

### 負面影響

* 輪詢的即時性不如 WebSocket 串流；最壞情況下畫面會落後一個快取 TTL 加一個輪詢週期。
* 快取是 in-memory 的 Caffeine，重啟即失；K 線目前**沒有落地到 Postgres**，所以「同一份資料可被 AI 訊號與模擬交易估值重用」目前只在單次執行期間成立。持久化留待後續 ADR 處理。
* 快取過期的同時若上游失敗，會直接把 5xx 傳給前端（沒有 stale-while-error 的降級路徑）；前端只能靠 `isStale` 標記維持舊畫面。
* symbol 驗證目前只有 `[A-Z0-9]{1,20}` 的格式檢查，沒有可交易標的白名單，等同對外開放一個 Binance 代理。
* 「輪詢不敷使用」的升級門檻尚未定義（沒有指標、沒有閾值），何時該轉 WebSocket 目前是主觀判斷。
* 實作綁在 Binance Spot 的可用性上，但轉接層（`MarketDataProvider` 介面）留了替換空間。
